# Payments: credit, the wallet and earnings

L402 credit tokens, the ledger, the wallet and the rate, earnings and withdrawals, and a strut buying from another strut.

This file is the reference for one area of strut; [AGENTS.md](../AGENTS.md) is the
index. A change in this area updates this file, not AGENTS.md.

## Files

What each file and folder in this area is, in the order of the tree.

### `src/l402.ts`

L402, the CREDIT TOKEN as bytes and rules (plans/paid-runs.md §4; item 5), pure — no wallet, no ledger: libmacaroons v2 binary (`encodeMacaroon` / `decodeMacaroon`, base64 std or URL-safe, at most 8 KB and 64 caveats; v1, JSON, a cut or trailing byte refused) and its HMAC chain (the root key derived through `macaroons-key-generator`, a third-party caveat chained as libmacaroons does), tested byte for byte against Go's `gopkg.in/macaroon.v2` (`src/fixtures/l402-macaroons.json`, made by `scripts/l402-fixtures/`); L402's identifier (66 bytes: version 0, the payment hash, a random token id); a token's root key `HMAC-SHA256(L402_ROOT, token id)`; STRUT'S CAVEATS, five, in order, on every token — `services=strut:0`, `strut_sats`, `strut_credit` (micro-dollars, the locked quote), `strut_valid_until` (unix s), `strut_carry` (the token it inherits from, or `none`: always written, so the fifth caveat is always strut's and a holder cannot append one) — and a HOLDER's (`strut_capabilities`, `strut_max_charge`, `strut_valid_until`, `services` still naming `strut:0`), each of which must hold; any other caveat, a third-party one, or strut's own again REFUSES the token (`readCaveats`, `narrowed`). `mintToken`, `addCaveat` (a holder's narrowing, from the macaroon alone), `parseAuthorization` (`L402` / `LSAT`, the preimage optional for `claim`), `verifyToken` (decode, chain, preimage, caveats: §4.3 steps 1–3, `L402Error`), `tokenRefusal` (this request: `expired`, `not_this_item`, `over_max_charge`)

### `src/public-credit.ts`

CREDIT, the service (plans/paid-runs.md §4, §5; item 5), what the `/public` routes call and items 6–9 reuse: `createCredit({ ledger, settings, rate, lightning })` → `verify` (src/l402.ts under `L402_ROOT`; 401 `invalid_token`), `use` (§4.3 step 4: the ledger knows the token, else its FIRST USE — the wallet's `lookup` must say settled, `ledger.firstUse` credits `strut_credit` in proportion to what settled at the quote's own rate, inheriting from `strut_carry`; concurrent requests for one token share one lookup, so the wallet is asked once; 503 `payment_pending` / `wallet_unavailable`, never 402), `check` (both), `challenge({ usd | sats, description, address, carry?, remaining?, reason? })` (the 402: a per-address allowance, `PUBLIC_INVOICES_PER_MINUTE` 20; the rate now, 503 `rate_unavailable`; sats rounded up; a ten-minute invoice, `PRICED_INVOICE_SECS`; a macaroon locking `strut_sats` / `strut_credit`, valid a year from the invoice's end; `WWW-Authenticate: L402 macaroon="…", invoice="…"` and §4.1's body; nothing stored; `L402_ROOT` minted if missing), `view(tokenId, { entries? })` (`GET /public/credit`'s balance: paid, spent, held, remaining in dollars and in sats at the token's rate, expired, replaced, the newest 50 entries), `claim(p, address)` (§4.4: the macaroon alone; pending / expired / settled with the preimage — whose answer records the first use; `PUBLIC_CLAIMS_PER_MINUTE` 120), `selling()` (`L402_ROOT` on file)

### `src/remote.ts`

A STRUT THAT BUYS (plans/paid-runs.md §10 "Another strut", item 9; the CVE case: an hourly automation running another strut's priced workflow): `createRemote({ store, http, withdraw, canPay, proposal, rate })` → `strut.remote` — `capability` (`ctx.services.remote`, frozen; what the `remote/*` steps are thin over), `check()` (the purchase keeper; `start()` every minute and at boot), `held()` (`GET /remote/credit`'s read: what is held where, never a token). A SELLER is a base URL (`sellerOf`: https only — the credit is a bearer credential — no credentials, query, trailing `/` or `/public`; a strut under a path, `…/lab`, is its own seller), reached through the guarded http, no peer record. The CREDIT held there is ONE L402 token per seller in `entitlements.json` (`ENTITLEMENTS_FILE`), an encrypted `FileSecretStore` file of its own beside `payments.json` (memory where strut keeps no files), `ENTITLEMENT_<sha256(seller)>` → `{ seller, credit?, purchase?, runs? }`; no step reads it (env.ts hides the `ENTITLEMENT_` prefix) and the capability presents it as `Authorization: L402 <macaroon>:<preimage>` and never hands it out, the peers capability's rule. SPENDING (decision 16, no ask): `list` (`GET <seller>/public`'s `runnable` + `credit`, the balance read with `GET /public/credit`), `launch` (`POST …/public/workflows/:name/run { input, key }`, tried again under the same key — the seller returns the run it started while in flight — on a 429, a 5xx or no answer, up to `LAUNCH_ATTEMPTS` 5, honouring `Retry-After` up to `LAUNCH_RETRY_AFTER_MAX_S` 120 s; the run TOKEN kept in the seller's record, `runs`, never returned and never in the run log; at most `RUN_TOKEN_KEEP_MS`, 7 days), `wait` (the launcher's view, `?wait=25`, until `charged` appears; a seller that does not answer — a network error, a 5xx, a 429 — is read again after a wait doubling to `RUN_READ_BACKOFF_MAX_MS` 30 s for as long as the step waits, the run being the seller's and charged either way; only 404 / 401 / 403 end it, `run_unknown:`; a `stale` run reported as it stands after `STALE_READS_MAX` reads), `cancel`, `release`, `call` (`POST …/public/steps/:type/run { config }`, the type's slashes kept; never sent twice — the seller's door takes no key: a failure there, 500 `step_failed` / `result_too_big` or 504 `timeout`, which the seller CHARGED, is `failed_charged:`, never "try again", and a lost answer `may_have_run:`). `launch` and `call` take the calling run's `control` and refuse (`spend_refused:`, `deps.spendRefusal`) in a run tree createStrut marks as never spending (`noRemoteSpend`: a stranger's public run, a peer-key launch with no person's credential, a run either started by `startedBy`; walked with run-control.ts `runLineage`) — decision 16's "no ask" is for this strut's own agents; a `replaced` 402 whose token changed since it was read (a purchase settled meanwhile) is sent once more with the new one. A 402 is `payment_required:` naming the seller's price in dollars and sats and why (none held, short, expired, replaced) and that an admin buys with remote/buy-credit — never a payment; a 401 `token_refused:`; `RemoteError { code, detail: { status, retryAfter, price } }`. `STRUT_REMOTE_LOCAL=1` (`allowLocal`) allows an `http:` seller and the guard's loopback and private addresses. BUYING (`buyCredit`, the door `remote/buy-credit` runs): only the ACCEPTED record on disk of that step for that seller and amount (the person's edits merged), as package/install's door; `no_pay_credential:` before anything else when the wallet cannot pay; ONE purchase per seller at a time (`purchase_in_flight:` — two would inherit one credit, and the second stored would drop the first; one never handed to the payer is dropped for the next). It asks `POST <seller>/public/credit { usd }` presenting the token held (it carries, §4.5; a 401 → asked again without), CHECKS the challenge before paying (invoice and macaroon name one payment hash; the macaroon is strut's five caveats, un-narrowed, its `strut_sats` the invoice's and its `strut_credit` at least the dollars accepted; not expired; the sats within `QUOTE_TOLERANCE`, 10%, of this server's own rate when it has one — `quote_too_high:`), keeps the PURCHASE in the record BEFORE paying, then pays through item 7's withdrawals service (`withdraw({ invoice, msat, actor, purpose: "purchase" })`: one payment per hash, its pending handling, its payer, one `withdrawal` entry with subject `purchase`). Settled with a preimage → stored at once; else the seller's `POST /public/credit/claim { macaroon }` is asked. A token is stored ONLY when its preimage hashes to its payment hash, and it REPLACES the one held (it inherited it). A purchase `pending` stays on file and `check()` claims it every minute until the seller says settled (stored) or `expired` (dropped: the invoice ended unpaid) — it never pays; the same proposal accepted again reuses the purchase's INVOICE (never a second payment), a withdraw error on a purchase already handed to the payer never drops it, and one whose invoice expired while the seller is silent is never dropped if it was sent (`remote_unavailable:`, kept and claimed) — until `PURCHASE_STUCK_AFTER_MS` (an hour) past the invoice, when the payer says the payment failed or never left (`deps.sendState`, createStrut's over `withdrawals.read`): a seller that rotated its L402 root or stopped selling never holds purchases back for good; one the payer says settled is kept for an admin, who drops it with `DELETE /remote/purchases?seller=` (`dropPurchase`, full scope)

### `src/run-cap.ts`

`resolveRunCap(workflowCap, env, fallback, runCap?)`: a run's cost cap — the workflow's `maxRunCostUsd`, else `STRUT_RUN_MAX_COST_USD`, else $100, and the smaller of that and the run's own (a public run's) — anything not positive an error. Its own module so core counts a public run's cap as the Mothership enforces it (mothership.ts re-exports it; core never imports mothership.ts)

### `src/payments/`
