# Packages, indexes and the store

Packages: the format, the build, the install and its doors, publishing and catalogs, indexes and the store front, working on a package as a git repo, and serve mode.

This file is the reference for one area of strut; [AGENTS.md](../AGENTS.md) is the
index. A change in this area updates this file, not AGENTS.md.

## Files

What each file and folder in this area is, in the order of the tree.

### `src/package-lookup.ts`

PACKAGE-FIRST lookup (plans/packages-ux.md §2): inside a package a bare name is the package's own item first (`<pkg>/<name>` when it exists), else the name as written — node's lookup, so nothing in a package is rewritten. An item's package is its name's prefix (`packagePrefixOf`, 3+ segments; workspace.ts re-exports it). Asked by the runner (`stepOfFrame` for a step's type, `workflowOfFrame` for a subflow's target — the frame's package is its OWN workflow's, `Exec.package`; events record the step and child that ran), the agent (`expandAgentTools(names, registry, ctx.package)`: a glob matches the package's and the strut's, the package's copy winning per name; a package's step is shown to the model by its name inside the package), the `run/*` steps and `meta/run-workflow` (`ctx.resolveWorkflow`), the app door (`runSingleStep` / `runStep` in the app's package), the app build (a package app's imports and granted workflows), an app release's lock, the closure walk (`flowClosure(…, scope)`: `run.start.stepHashes`, the ledger's subjects) and the install's checks (a check's step written as the package's). `ctx.package` + `ctx.resolveWorkflow` are the runner's to set

### `src/tar.ts`

tar / untar: a ustar archive of regular files — a package archive and a move. A name past 100 bytes split into ustar's prefix; one no split holds (a Concept page's long node key) in a POSIX PAX extended header (`path=`) before its entry, so an archive with no long name is the same bytes it always was. The reader (`TarNames`, also a move's streaming reader) takes PAX `x` (`path`, `size`) and GNU `L` long names, reads past a PAX global `g`, and refuses a non-file entry, a name twice, a cut archive, all by the whole name. A strut from before 2026-11-09 refuses an archive with a PAX header (a non-file entry)

### `src/packages/`

PACKAGES (plans/marketplace.md): the bytes, the build, and the install from `file:`, `pk:` and `git+` (steps 1–2, the HTTP-first half of 6 and the `git+` source of 3, apps included), and the round trip with a git repo (plans/app-repos.md §3, repos.ts below; a person's update is a later item). format.ts: a package is a directory, `strut.yaml` (zod, strict: `package: publisher/name` lowercase, `version`, `description?`, `requires { secrets, binaries, runtimes, packages: [{ package, digest, source }] }`) and `workflows/<path>.yaml`, `steps/<path>.ts` (`_` files helpers, `<name>.claims.yaml` beside a step), `concepts/<file>.md` (a Concept page, named by the `name` in its front matter whatever its file — the new form, which a build writes as `concepts/<key>.md` with every attribute and every parent — or, in the old form, by its file), `apps/<name>/` (with app.yaml), `graph/<Type>.yaml` (a graph type, item kind `type`, named by its type; graph-types.ts); `readPackage(dir)` → `{ manifest, digest, files, items }`, each item named `<package>/<path>` (a Concept by its page name), refusing with `bad_package:` an unknown top-level folder, a file a folder does not hold, a name the step/app rules refuse, two Concept pages with one name, a symlink, a package with no items. The DIGEST is `sha256:` + `hashTree` (src/version.ts, `treeHash`'s function) over every file but dotfiles, `node_modules/` and each app's `dist/` + `data.db` (`packageExcluded`), `strut.yaml` included — so an app inside hashes as its version hash does. cache.ts: `<dataDir>/packages/sha256-<hex>/`, one directory per digest, written once through a scratch directory that is re-read and hashed before the rename (`PackageCache`: `get` re-hashes, `putDir`, `putArchive`); `resolvePackage(ref, { cache, digest?, base?, url?, fetch?, tokenSecret?, secret?, shell?, dataDir?, known? })` — `file:` copies a directory in, `pk:` goes through pk.ts, `git+` through git-source.ts. git-source.ts: the `git+<repo>[@<branch|tag|commit>][#<folder>]` SOURCE (§5; plans/app-repos.md §2, §4.7) — the repo any URL `git/checkout` takes (`parseRepo`: http(s) or `file://`, no credentials), the ref the remote's default branch when left out, `#<folder>` where `strut.yaml` is; fetched into git/checkout's own bare cache under `<dataDir>/repos/` (`fetchCache`, `remoteDefaultBranch`, `commitOf` in steps/lib/git/_shared.ts, which checkout.ts runs too) under its per-cache lock, the token — the secret `tokenSecret` names, default `GITHUB_TOKEN`, read as the installing actor where actor secrets are kept — in the child env behind the inline credential helper only and masked out of every error; the ref resolved as the remote's branch, then a tag, then a commit (never a branch an agent made in the cache), the tree at that commit under `#<folder>` written out through a throwaway index outside the cache (`read-tree` + `checkout-index`), then put in the cache by digest. Refusals name what failed: `package_repo_not_found:`, `package_repo_denied:` (credentials asked for or refused, naming the secret), `package_repo_unreachable:`, `package_ref_not_found:`, `package_source_invalid:` (`#<folder>` not there, or no `strut.yaml` in it), `package_digest_mismatch:` with the commit. The install records the commit on every version it writes (`upstream.commit`, beside `source.ref` as written — what an update re-resolves, a branch or a tag, never the commit; `commit` on `GET /packages` and the install report); a pinned `git+` requirement the cache holds is taken from it, as `file:` is; `known: { commit, digest }` answers a ref still at that commit from the cache without reading the tree out (serve mode). Every door takes it: `POST /packages/install { ref, tokenSecret? }`, `STRUT_PACKAGES` (an entry is here when an installed package records that very ref), a `requires.packages[].source` (the token only for a requirement on the origin of a ref the person named: a package never sends it to a host of its choosing). pk.ts: the `pk:<key>/<publisher>/<name>[@digest]` SOURCE (§5, §13, HTTP-first 2026-10-28) — the publisher's catalog fetched from `url` (where it is served today: a strut's `/packages/catalog?public=1`, or an uploaded file; later an index row's or the key's Pkarr record, neither changing a check) and read as a card against the KEY, its `seq` against the last accepted from that key on this strut (`<dataDir>/packages/index/<key>.json`), the release (the pin, which the catalog must list — `package_not_published` — else the newest not yanked), its archive by digest from the route beside the catalog (`releaseUrls`: the catalog's own query rides along) then the release's `urls`, and every required package the catalog lists, so the install finds them cached; the install pins `upstream.key` and `upstream.source.url`. archive.ts: the archive is the PLAIN TAR of the files (`packTar`: the digest's order, src/tar.ts's layout, pinned by a test vector — the same bytes on every strut that holds the package, what its torrent hashes; plans/marketplace.md §13), served with `format=tar` and gzipped without it for a strut from before, transport only; `unpackArchive` reads either, and `fetchArchive` checks a plain tar against the release's `tar.sha256` before unpacking it. torrent.ts: `packageTorrent(digest, tar, { webSeeds? })` — the plain tar's single-file v1 torrent built one fixed way (`name` the digest hex + `.tar`, 256 KiB pieces, nothing else in the info dict), so its infohash follows from the digest; `bencode`; nothing seeds yet (plans/torrents.md §8). A catalog release names `tar: { sha256, infohash }` (card.ts), set by `POST /packages/publish` — `unpackArchive` refuses a path that leaves the directory or one the digest never covers, caps size and count; `archiveProblem` packs a package as the route does and reads it back as `unpackArchive` would, which `buildPackage` (dry run included) asks before keeping anything, so a package no strut could fetch is refused at the build (`package_unarchivable:`); `fetchArchive({ urls, digest, cache, package?, headers? })` returns the cached digest or fetches from the first URL whose archive unpacks to it, passing over the rest and naming each (never a query) — the last hop of the later `pk:` resolver. `GET /packages/:publisher/:name/archive?digest=` (createStrut) serves any package the cache holds, behind the gate. install.ts: `installPackage(deps, ref, { digest?, actor? })` — the package and, FIRST, every `requires.packages` pin not installed here at that digest (the cache, else the pin's source, a relative `file:` from the requiring package's directory); ALL OR NOTHING: every name and file of the set checked before the first write (a local item under the prefix, a sealed namespace, a Concept under someone else's stamp or with a parent nowhere, an attribute the graph's `Concept` does not declare a warning, a workflow naming a step / grant / subflow neither here nor in the set or whose `name:` is not its path, a claims file that does not parse), each app copied out of the cache and BUILT against this strut's kit with the set's workflows and apps in reach; then steps (`source: "install"`, `upstream`, the actor), one registry rebuild and a load check (a step that does not load, or whose `defineStep` type is not its path, takes back everything written), workflows (owned by the actor), apps through `ctx.services.apps`' publish (a person's, each after the set's apps it imports — so what an app publish does, an install does), Concepts through `seedConcepts` stamped `pkg/<package>/` with `keepEdited`, then the claims with the package as speaker and the publish checks (a claim that will not record is a warning, never a take-back). The same digest again installs what is missing; another digest through a person's door is `package_update_not_built:` (it asks first, not built). The DISTRO's door (`strut.packages.install(ref, { door: "distro" })`, in process only, plans/marketplace.md §12) applies a release with no ask and UPDATES item by item (§4's table): an item whose active version the package wrote (`source: install | distro` + `upstream`) is fast-forwarded, a fork gets the release's version beside it (`activate: false`, `diverged`), an item the release drops is retired when untouched and kept when forked, an edited Concept is left out of the seeder's set; a required package at a new digest is updated first; versions record `source: "distro"` and the package is then the distro's (`package_distro_owned:` at a person's door). A REPO's door (`door: "repo"`, in process only — repos.ts calls it) applies a commit of a checkout this strut works on, and the commit is the truth (the workspace's edits were committed into it first): every item is made what the commit holds, a fork too (`update`); a version whose content is the commit's already is STAMPED with it in place (`PublishOptions.stamp`: its `source`, `actor` and `upstream` rewritten on the known version, no new one — status `stamped`, written after everything else went in); what the commit dropped is retired whatever its state; a Concept page made here (no stamp) under a page's name is taken as the package's (`ConceptSet.adopt`); a package installed by another door is refused (`package_conflict:`). The repo door takes local items under the prefix (and adopts unstamped pages) only for a package it installed already — an open repo's apply, or a reopen after Close — and pages for Create repo's open (`adoptPages`); a FIRST Open refuses them, as a person's door does. A package the repo door installed is written by no other door (`package_repo_owned:`, `repoOwned`: a person's install, the distro's), and `strut.packages.uninstall` refuses it while its repo is open. Every step an install makes active is TRIAL-LOADED from `<cache>/.install/<rand>/trial/` before the first write (`stepFileType`, registry.ts), since no store deletes one version; a later failure re-points an updated item at its previous version. The fold's `installed` is the active version when the package wrote it, else the newest the package wrote, and the package's digest is its newest installed version's.
