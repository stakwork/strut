# Packages, indexes and the store

Packages: the format, the build, the install and its doors, publishing and catalogs, indexes and the store front, working on a package as a git repo, and serve mode.

This file is the reference for one area of strut; [AGENTS.md](../AGENTS.md) is the
index. A change in this area updates this file, not AGENTS.md.

## Files

What each file and folder in this area is, in the order of the tree.

### `src/package-lookup.ts`

PACKAGE-FIRST lookup (plans/packages-ux.md §2): inside a package a bare name is the package's own item first (`<pkg>/<name>` when it exists), else the name as written — node's lookup, so nothing in a package is rewritten. An item's package is its name's prefix (`packagePrefixOf`, 3+ segments; workspace.ts re-exports it). Asked by the runner (`stepOfFrame` for a step's type, `workflowOfFrame` for a subflow's target — the frame's package is its OWN workflow's, `Exec.package`; events record the step and child that ran), the agent (`expandAgentTools(names, registry, ctx.package)`: a glob matches the package's and the strut's, the package's copy winning per name; a package's step is shown to the model by its name inside the package), the `run/*` steps and `meta/run-workflow` (`ctx.resolveWorkflow`), the app door (`runSingleStep` / `runStep` in the app's package), the app build (a package app's imports and granted workflows), an app release's lock, the closure walk (`flowClosure(…, scope)`: `run.start.stepHashes`, the ledger's subjects) and the install's checks (a check's step written as the package's). `ctx.package` + `ctx.resolveWorkflow` are the runner's to set

### `src/tar.ts`

tar / untar: a ustar archive of regular files — a package archive and a move. A name past 100 bytes split into ustar's prefix; one no split holds (a Concept page's long node key) in a POSIX PAX extended header (`path=`) before its entry, so an archive with no long name is the same bytes it always was. The reader (`TarNames`, also a move's streaming reader) takes PAX `x` (`path`, `size`) and GNU `L` long names, reads past a PAX global `g`, and refuses a non-file entry, a name twice, a cut archive, all by the whole name. A strut from before 2026-11-09 refuses an archive with a PAX header (a non-file entry)

### `src/packages/`

PACKAGES (plans/marketplace.md): the bytes, the build, and the install from `file:`, `pk:` and `git+` (steps 1–2, the HTTP-first half of 6 and the `git+` source of 3, apps included), and the round trip with a git repo (plans/app-repos.md §3, repos.ts below; a person's update is a later item). format.ts: a package is a directory, `strut.yaml` (zod, strict: `package: publisher/name` lowercase, `version`, `description?`, `requires { secrets, optional (secrets a step may read that neither the gate nor an install's `missing` asks for; the fence is both lists, `readableSecrets`; recorded as `upstream.optional` and shown apart on `GET /packages` as `optional`, so a host offers to set only what a package requires; `GET /packages` also reports each package's `missing: { secrets }`, the required ones the deployment has no value for, read as the gate reads them, its store then strut's environment, `withMissingSecrets` in installed.ts — a host asks an admin for those, never `GET /secrets`, which lists the store alone and so asks again for what strut takes from its environment, as Stadeum's `PODS_URL` and `PODS_TOKEN`), binaries, runtimes, packages: [{ package, digest, source }] }`, `job { tools, approve? }`, `provides { secrets, git }` (`secrets`: the ones its steps manage, each one they may read — else `bad_package` — the fence's second list; `git: [{ host, secret, repositories?, pull_request? }]`: the hosts a token it holds serves, a lowercase hostname with `:port` when not the default, each with a secret its steps may read, a host named once — src/git-hosts.ts, docs/security.md "Git credentials by host" — and the FORGE'S STEPS for that host (plans/package-seams.md §4): `repositories` (what the token reaches) and `pull_request` (opening one), each the package's own step by `<name>` first, else strut's by its type (`github/create-pr`), never another package's (`provides.git[i].<field>: … is another package's step`); `readPackage` resolves them to full types (`PackageInfo.gitHosts`), which the install records on `upstream.provides.git` and checks: each a step on this strut or in the package (`…'s pull_request names the step …, which is neither on this strut server nor in the package`), and none that another holder of the host names differently, strut's own `github.com` → `github/create-pr` included (`gitHostProblems`, a 409); strut's `git/repositories` and `git/pull-request` pick them by host, docs/steps.md; `GET /packages` shows both), `requires.git: true` (its steps read the run's token for a repository's host themselves, `secrets.git(url)`; recorded as `upstream.git`, shown on `GET /packages` and the store page), `schedules [{ workflow, name?, trigger, input?, each? }]` (workflows of the package strut runs on a schedule; below), `maxRunCostUsd { <workflow>: <dollars> }` (the most one run of a workflow of the package may spend; below), `on [{ created|updated|deleted: <Type>, workflow }]` (workflows of the package strut runs on a graph write; below), `calls { kind, app }` (what a group call on the box records onto; below), `bundle: [<git+ ref>, …]` (a BUNDLE, below)) and `workflows/<path>.yaml`, `steps/<path>.ts` (`_` files helpers, `<name>.claims.yaml` beside a step), `concepts/<file>.md` (a Concept page, named by the `name` in its front matter whatever its file — the new form, which a build writes as `concepts/<key>.md` with every attribute and every parent — or, in the old form, by its file), `apps/<name>/` (with app.yaml), `graph/<Type>.yaml` (a graph type, item kind `type`, named by its type; graph-types.ts); `readPackage(dir)` → `{ manifest, digest, files, items, job? }`, each item named `<package>/<path>` (a Concept by its page name), refusing with `bad_package:` an unknown top-level folder, a file a folder does not hold, a name the step/app rules refuse, two Concept pages with one name, a symlink, a package with no items. A BUNDLE (stadeum plans/software.md §3.3, §5 item 5) is a manifest whose `bundle:` lists other packages, each by the `git+<repo>[@<branch>][#<folder>]` ref it is followed at, with no digest; `readPackage` reads it as `items: []` (`readBundle`) and refuses with `bad_package:` a folder of any kind (`<top>/: a bundle lists packages and holds no items of its own`), `requires`, `job`, `provides`, `schedules` or `maxRunCostUsd` (`…: a bundle lists packages and has no <key> of its own`), an empty list, an entry that is not a branch a subscription can follow (`branchRefProblem`, git-source.ts: not `git+`, or a full commit sha) and one repository folder listed twice at any branch (`refSource`). Whether a listed package is itself a bundle is known only once it is read: its part fails then (subscriptions.ts). An older strut refuses the key (the schema is strict). Nothing installs a bundle: `resolveSet` refuses one, as a ref asked for or a requirement, `package_is_bundle: … subscribe to its repository` (400), so `POST /packages/install`, the boot list and serve mode refuse it. The manifest's `job:` (plans/followed-repos.md §3; stadeum plans/software.md §5, item 16) names the steps the `job` workflow's agent may call: `tools`, and `approve`, the ones among them whose call is a proposal. A name is the package's OWN step first, as every bare name in a package is (src/package-lookup.ts: `claim` → `<package>/claim` when it ships `steps/claim.ts`); a name it does not ship is STRUT's step of that type (`git/push`), named one by one; a glob is over its own steps alone (`*`: every step it has; `_` helpers are not steps), so an older manifest reads exactly as it did and a glob never reaches strut's steps. `readPackage` resolves both into `job: { tools, approve }`, full types deduplicated and sorted (`strutGrants(pkg, types)`: the ones not under its prefix are strut's), and refuses a glob that matches none of its steps, a helper, a name of three segments or more (another package's step, never granted, or its own by full type; plans/followed-repos.md Decided 10 refused strut's steps too, which item 16 reverses), a name the step rule refuses and an `approve` step not among the tools. Whether strut has the step, and may hand it out, is the install's: `checkSet` holds each one to `strutGrantProblem` (src/job-seed.ts, docs/security.md "A package's grant of strut's steps") — strut's own (core or lib, `PackageDeps.stepSources`), not sealed, its config naming no secret, declaring its `effect` — and refuses the package `bad_package: strut.yaml: job.tools: <why>` otherwise, before anything is written. The manifest is strict, so a strut from before the key refuses such a package instead of installing it without its tools (Decided 9). The `job` seed grants it (src/job-seed.ts, docs/jobs.md). A build (`buildPackage`) writes a manifest with no `job:`; a package that grants is written by hand, in its repo. The manifest's `schedules:` (stadeum plans/software.md §5 item 3) names workflows OF THE PACKAGE strut runs on its own, each an automation's draft — `name?` (the workflow's name inside the package unless given; unique, its identity across releases), `trigger` (the automations' grammar, `triggerSchema` in src/automations.ts, the one "how often" strut has; held strict, so a key no shape has is refused, not dropped; never `once`), `input?` (fixed in the manifest; templates over `now`, `today`, `last` only, `checkInputTemplates`) and `each?` (a secret the package provides, `provides.secrets`: each fire runs the workflow once for each person who holds it as their own, as that person, from their own `last`; docs/automations.md, "A schedule for each person") — with its `workflow` by its name inside the package; `readPackage` resolves them into `schedules: [{ name, workflow (full), trigger, input, each? }]` and refuses a workflow the package does not carry, two of one name, an `each` the package does not provide, and what the grammar refuses, each `strut.yaml: schedules[i]…`. Strict like the rest, so a strut from before the key refuses the package instead of installing it without its schedules. schedules.ts: `installedSchedules(deps)` reads each installed package's resolved `schedules` from the cache by the digest installed while it `holdsItsOwn` (installed.ts; the rule `job:` grants follow) — a package the cache cannot read is `unread`, and keeps what it has — and createStrut's `syncSchedules` hands them to the automations' `syncPackageSchedules` (src/scheduler.ts, docs/automations.md) at boot and after every package write (`oneAtATime`, beside the `job` re-seed): each is an ordinary automation marked `package`, id `packageAutomationId(package, name)`, so an install makes it, a release follows it (on or off kept), an uninstall drops it (the one that keeps a fork too), and a restart, a reinstall or a restore leaves one. The store's detail (detail.ts) lists each on its workflow as a sentence (`WorkflowDetail.schedules`), the zone said only when the schedule names one. WHAT A CALL RECORDS ONTO (stadeum plans/call-canvas.md §8): the manifest's `calls: { kind, app }` — `kind`, the scribe's job kind, the name of a Concept page the package ships (the old form's file or the new form's `name`), and `app`, the app Jamie's screen shows, one of the package's apps by its folder (`canvas` → `stadeum/canvas/canvas`). `readPackage` resolves it into `calls: { kind, app (full) }` and refuses a kind the package has no page for and an app it has no folder for (`strut.yaml: calls.kind: …`, `calls.app: …`), so the install fails with `bad_package`; strict, so an older strut refuses the package; a bundle has none. The install records it on every version it writes (`upstream.calls`, a JSON property, no schema change), and `GET /packages` lists it with the package (`InstalledPackage.calls`, installed.ts), dropped once the package no longer `holdsItsOwn` (uninstalled, a fork kept), as its job grant and schedules are. Why: sphinx-voice named the canvas in its own code (`VOICE_SCREEN_APP`, `CALL_CANVAS_KIND`), so a box without the canvas package recorded into a job with no page and showed an app that was not there. Voice now reads `GET /packages` and records onto every package that has `calls` — a job of each kind, the screen the first package's app by name — and a box with none has no recording. Strut's `/voice/calls` routes are unchanged: they forward the body as it came. WORKFLOWS ON GRAPH WRITES (plans/package-seams.md §2): the manifest's `on:` names workflows OF THE PACKAGE strut runs when a node of a type is created, updated or deleted — each entry exactly one op naming a graph type (`created: Workspace`, the type grammar of `graph/<Type>.yaml`) and the `workflow` by its name inside the package (`{ created: Workspace, workflow: setup }`); `readPackage` resolves them into `on: [{ op, type, workflow (full) }]` and refuses a workflow the package does not carry, an entry with no op or two, the same entry twice, each `strut.yaml: on[i]…`; strict, so an older strut refuses the package (and an `event:` entry, planned beside them, is refused until it is built); a bundle has none. on.ts: `installedTriggers(deps)` reads them as the schedules are read (by the digest installed, while the package `holdsItsOwn`; `unread` keeps what it had), and createStrut's `syncOn` holds them in memory at boot and after every package write, so an install adds them and an uninstall drops them. What fires them is any write strut hears (src/graph-writes.ts, docs/graph.md): every run's graph view hands each SEND of its reporter (a second after its last write, and at its end) to the bag's `onWrites`, its node writes folded to one op per node (`netOps`: created then updated → `created`; created then deleted → nothing; updated then deleted → `deleted`; deleted then restored → `updated`; strut's own types and a node whose type the send could not learn left out) — a proposal's apply too, `by` its `proposal:<id>`; never a write on a Concept branch or in a trial (bindGraph gives such a view no `onWrites`), raw Cypher or another process's. `matches` turns each write into launches: none with no person behind the writing run (its actor, else its principal — an unattended run's workflow owner); none of the package whose `on:` started the writing run; none past `ON_CHAIN_MAX` (3) runs in a chain, each stopped one a warning in the server's log naming the run. createStrut's `launchOn` launches each match DETACHED as the writing run's person (so on their tokens and their bill), input `{ ref_id, type, op, by, job?, node? }` (`by` the writing run's id, `job` its job when it has one — so a workflow tells a job's write from a person's; after `deleted` the node may be gone, so a `deleted` carries `node`, its values as they were: read in the node writer's delete wrapper just before the delete, where its type is read, and capped by `lastValues` in graph-writes.ts to small scalar fields — a string up to 1,000 characters (`NODE_VALUE_MAX`), a number or a boolean, 16,000 characters in all (`NODE_VALUES_MAX`) — so a Concept's body or an embedding never lands in a run's input; carried through `netOps` and `NodeWrite.node`, never to the feed or the job; a workflow with an `input:` block declares `node: { type: json, required: false }`, which the block drops otherwise), with the run's `onWrite` mark (`OnWriteMark` in core.ts: package, op, type, ref_id, by, depth) on `run.start` — kept by a resume and handed to the run's own graph view, which is what holds it to its chain. The mark is the run's WORK's: a job run it starts (`job/start`, `startedBy` the marked run) is launched with it too, and a nested run's writes take its parent's (`onWriteMarkOf`, the controller tree) — so an `updated:` entry whose workflow starts a job that updates the node does not start itself again; a detached `run/launch` from it carries none; a disabled workflow or a failed launch is a warning, and nothing retries. The fence takes `onWrites` off a package step's bag (it names a person). The store's detail says each on its workflow (`WorkflowDetail.on`: "when a Workspace is created, as the person whose run did it"). The manifest's `maxRunCostUsd:` caps a run of a workflow OF THE PACKAGE, by its name inside it, in dollars: `maxRunCostUsd: { reply: 1 }`. It is the cap an admin sets with `PUT /workflows/:name/run-cap` (docs/models.md "Mothership cost control"), shipped by the package; no new kind of limit. `readPackage` resolves it to `maxRunCostUsd: { <full name>: <dollars> }` and refuses a workflow the package does not carry and a cap that is not a positive number, each `strut.yaml: maxRunCostUsd.<name>: …`; a bundle has none. Strict like the rest, so a strut from before the key refuses the package instead of running it under the box's default cap. The install records it on the version it writes or stamps (`upstream.maxRunCostUsd`, workflow versions only), so a release follows it as it follows the fence: a release that changes only strut.yaml stamps the version with the new cap, and one that drops it drops it. A run's cap is an admin's own first (`WorkflowMetadata.maxRunCostUsd`), then the package's on the active version, then `STRUT_RUN_MAX_COST_USD`, then $100 (`workflowRunCap`, src/run-cap.ts). A release never writes the admin's, so an admin's cap stays; cleared, the package's is the cap again. It lives on no record of its own: an uninstall deletes the workflow and the cap with it, so a workflow later made under the name has none, and a fork the uninstall keeps keeps its versions as they were, cap included, as it keeps their fence. `GET /workflows` says it as `packageMaxRunCostUsd` beside the admin's `maxRunCostUsd`; the store's detail says it on its workflow (`WorkflowDetail.maxRunCostUsd`). Tests: src/packages/run-cap.test.ts. The DIGEST is `sha256:` + `hashTree` (src/version.ts, `treeHash`'s function) over every file but dotfiles, `node_modules/` and each app's `dist/` + `data.db` (`packageExcluded`), `strut.yaml` included — so an app inside hashes as its version hash does. cache.ts: `<dataDir>/packages/sha256-<hex>/`, one directory per digest, written once through a scratch directory that is re-read and hashed before the rename (`PackageCache`: `get` re-hashes, `putDir`, `putArchive`); `resolvePackage(ref, { cache, digest?, base?, url?, fetch?, gitSecret?, secret?, shell?, dataDir?, known?, branch? })` — `file:` copies a directory in, `pk:` goes through pk.ts, `git+` through git-source.ts. git-source.ts: the `git+<repo>[@<branch|tag|commit>][#<folder>]` SOURCE (§5; plans/app-repos.md §2, §4.7) — the repo any URL `git/checkout` takes (`parseRepo`: http(s) or `file://`, no credentials), the ref the remote's default branch when left out, `#<folder>` where `strut.yaml` is; fetched into git/checkout's own bare cache under `<dataDir>/repos/` (`fetchCache`, `remoteDefaultBranch`, `commitOf` in steps/lib/git/_shared.ts, which checkout.ts runs too) under its per-cache lock, the token — the one for the repository's host: the secret that serves it (`gitSecret`, the box's map; strut's own `github.com` → `GITHUB_TOKEN` without one) read through `secret(name)` as the door reads it (the installing actor's own first where actor secrets are kept), none for a host no secret serves, a `file:` repository or plain http to another machine — in the child env behind the inline credential helper, which answers that host alone, and masked out of every error; no caller names the secret (`tokenSecret`, gone 2026-11-20: a door refuses it, `TOKEN_SECRET_GONE`; `STRUT_PACKAGES` and `STRUT_SERVE_TOKEN_SECRET` leave an old one unread so a box still boots); the ref resolved as the remote's branch, then a tag, then a commit (never a branch an agent made in the cache; with `branch: true`, what a subscription reads, the branch alone, so a tag or a commit is `package_ref_not_found: … a subscription follows a branch`), the tree at that commit under `#<folder>` written out through a throwaway index outside the cache (`read-tree` + `checkout-index`), then put in the cache by digest. Refusals name what failed: `package_repo_not_found:`, `package_repo_denied:` (credentials asked for or refused, naming the secret), `package_repo_unreachable:`, `package_ref_not_found:`, `package_source_invalid:` (`#<folder>` not there, or no `strut.yaml` in it), `package_digest_mismatch:` with the commit. The install records the commit on every version it writes (`upstream.commit`, beside `source.ref` as written — what an update re-resolves, a branch or a tag, never the commit; `commit` on `GET /packages` and the install report); a pinned `git+` requirement the cache holds is taken from it, as `file:` is; `known: { commit, digest }` answers a ref still at that commit from the cache without reading the tree out (serve mode). Every door takes it: `POST /packages/install { ref }`, `STRUT_PACKAGES` (an entry is here when an installed package records that very ref), a `requires.packages[].source` (a token only for a requirement on the host of a ref the person named, `gitHostOfRef`: a package never spends one on a host of its choosing). pk.ts: the `pk:<key>/<publisher>/<name>[@digest]` SOURCE (§5, §13, HTTP-first 2026-10-28) — the publisher's catalog fetched from `url` (where it is served today: a strut's `/packages/catalog?public=1`, or an uploaded file; later an index row's or the key's Pkarr record, neither changing a check) and read as a card against the KEY, its `seq` against the last accepted from that key on this strut (`<dataDir>/packages/index/<key>.json`), the release (the pin, which the catalog must list — `package_not_published` — else the newest not yanked), its archive by digest from the route beside the catalog (`releaseUrls`: the catalog's own query rides along) then the release's `urls`, and every required package the catalog lists, so the install finds them cached; the install pins `upstream.key` and `upstream.source.url`. archive.ts: the archive is the PLAIN TAR of the files (`packTar`: the digest's order, src/tar.ts's layout, pinned by a test vector — the same bytes on every strut that holds the package, what its torrent hashes; plans/marketplace.md §13), served with `format=tar` and gzipped without it for a strut from before, transport only; `unpackArchive` reads either, and `fetchArchive` checks a plain tar against the release's `tar.sha256` before unpacking it. torrent.ts: `packageTorrent(digest, tar, { webSeeds? })` — the plain tar's single-file v1 torrent built one fixed way (`name` the digest hex + `.tar`, 256 KiB pieces, nothing else in the info dict), so its infohash follows from the digest; `bencode`; nothing seeds yet (plans/torrents.md §8). A catalog release names `tar: { sha256, infohash }` (card.ts), set by `POST /packages/publish` — `unpackArchive` refuses a path that leaves the directory or one the digest never covers, caps size and count; `archiveProblem` packs a package as the route does and reads it back as `unpackArchive` would, which `buildPackage` (dry run included) asks before keeping anything, so a package no strut could fetch is refused at the build (`package_unarchivable:`); `fetchArchive({ urls, digest, cache, package?, headers? })` returns the cached digest or fetches from the first URL whose archive unpacks to it, passing over the rest and naming each (never a query) — the last hop of the later `pk:` resolver. `GET /packages/:publisher/:name/archive?digest=` (createStrut) serves any package the cache holds, behind the gate. install.ts: `installPackage(deps, ref, { digest?, actor? })` — the package and, FIRST, every `requires.packages` pin not installed here at that digest (the cache, else the pin's source, a relative `file:` from the requiring package's directory); ALL OR NOTHING: every name and file of the set checked before the first write (a local item under the prefix, a sealed namespace, a Concept under someone else's stamp or with a parent nowhere, an attribute the graph's `Concept` does not declare a warning, a workflow naming a step / grant / subflow neither here nor in the set or whose `name:` is not its path, a claims file that does not parse), each app copied out of the cache and BUILT against this strut's kit with the set's workflows and apps in reach; then steps (`source: "install"`, `upstream`, the actor), one registry rebuild and a load check (a step that does not load, or whose `defineStep` type is not its path, takes back everything written), workflows (owned by the actor), apps through `ctx.services.apps`' publish (a person's, each after the set's apps it imports — so what an app publish does, an install does), Concepts through `seedConcepts` stamped `pkg/<package>/` with `keepEdited`, then the claims with the package as speaker and the publish checks, then its pages' `claims:` blocks with their cases and the checks each names (`pageClaims` → `trials.seed`, docs/knowledge.md "Trials and tests"; a claim that will not record is a warning, never a take-back). The same digest again installs what is missing; another digest through a person's door is `package_update_not_built:` (it asks first, not built). The DISTRO's door (`strut.packages.install(ref, { door: "distro" })`, in process only, plans/marketplace.md §12) applies a release with no ask and UPDATES item by item (§4's table): an item whose active version the package wrote (`source: install | distro` + `upstream`) is fast-forwarded — or, when its content is the release's already from another release, or from this one put here by another door or source (a person's install, the boot list, a subscription since stopped — which this source now follows), STAMPED the release's in place (`stamped`, no new version, the registry rebuilt for a step's fence), so a release that changes only its `strut.yaml` (`job:`, `provides`, `schedules:`) is what the fold reads as installed — a fork gets the release's version beside it (`activate: false`, `diverged`), an item the release drops is retired when untouched and kept when forked, an edited Concept is left out of the seeder's set; a required package at a new digest is updated first; versions record `source: "distro"` and the package is then the distro's (`package_distro_owned:` at a person's door). Every door's publish is a `stamp` (`PublishOptions.stamp`): a release whose item is a version here already — a branch or channel moved back, a release beside a fork whose content an older version holds — writes no version but rewrites that one's `source`, `actor` and `upstream` with the release's, and every `upstream` a release writes or stamps carries `at`, the time it went in (one for the whole release). A REPO's door (`door: "repo"`, in process only — repos.ts calls it) applies a commit of a checkout this strut works on, and the commit is the truth (the workspace's edits were committed into it first): every item is made what the commit holds, a fork too (`update`); a version whose content is the commit's already is STAMPED with it in place (`PublishOptions.stamp`: its `source`, `actor` and `upstream` rewritten on the known version, no new one — status `stamped`, written after everything else went in); what the commit dropped is retired whatever its state; a Concept page made here (no stamp) under a page's name is taken as the package's (`ConceptSet.adopt`); a package installed by another door is refused (`package_conflict:`). The repo door takes local items under the prefix (and adopts unstamped pages) only for a package it installed already — an open repo's apply, or a reopen after Close — and pages for Create repo's open (`adoptPages`); a FIRST Open refuses them, as a person's door does. A package the repo door installed is written by no other door (`package_repo_owned:`, `repoOwned`: a person's install, the distro's), and `strut.packages.uninstall` refuses it while its repo is open. PULL: the package's folder put back to HEAD and the edits committed locally first (`local`, no push), `fetchCache`, `git merge` of `origin/<branch>`; a conflict names the unmerged files, installs nothing, and is kept on the record (`merge`: until the merged tree is applied nothing more is written from the workspace, and Commit waits) — the person resolves in the working copy and Pulls again, which concludes the merge; else the merged tree is applied. CREATE (`POST /packages/repos/create`, a `BuildRequest` + `{ url, branch?, path? }`): refused before anything is pushed when the name is installed here or items made here are under it, built (`buildPackage`), pushed as the first commit of an EMPTY remote (`package_repo_not_empty:` otherwise), opened (its pages adopted); the bare items it was built from are `originals`, retired only by `…/retire` on the person's word. CLOSE (`DELETE`): the record and the working copy go, the items stay, and the prefix takes no new name again (an added, uncommitted item stays local, editable, written by the first Commit after the repo is opened again). The token: the one for the repository's host (`authOf`: the secret that serves it, src/git-hosts.ts), the actor's own first, through `_shared.ts`' credential helper for that host only, masked out of every error; a commit's GitHub identity and a pull request only on github.com, as before. The agent's door is `package/commit` (steps/lib/package/commit.ts): a proposal an ADMIN accepts, checked against the accepted record on disk (`ctx.services.packages.commit`); the `job`, `builder` and `orchestrator` seeds grant it and list it in `approve:`. Git merges; strut never does. A REPO'S PAGES ARE FROM GIT (plans/concept-evals.md item e, src/concept-sources.ts): a change a merge of a Concept branch or the dream makes to a page stamped `pkg/<package>/` is never made in the graph; where the package is opened here it is a `knowledge/write-pages` proposal an ADMIN accepts, which writes the page's file into the working copy (`concepts/<file>` as the stamp names it, the page's form kept: its front matter byte for byte when only the docs changed) and reloads the package's pages from there (`seedConcepts` with the repo door's `keepEdited` + `adopt`), so the next Commit has the page as an edit and makes the branch and the PR; a removed page is a file removed and its node retired; a repo waiting on a merge refuses it (`no_checkout:`). A package installed any other way (an index, `git+`, `file:`) has no working copy: the change is skipped, and the answer says so. subscriptions.ts: this strut FOLLOWING another's catalog (§12.1) — `{ key, url, channel?, token? }` in an encrypted file of its own, `subscriptions.json` (the operator's full-scope `PUT /packages/subscriptions/:id`), its state beside the cache (`<dataDir>/packages/subscriptions/`: the catalog accepted, the release applied); a SYNC (at the `PUT`, at boot, every `STRUT_DISTRO_POLL_MINUTES`, on the publisher's ping `POST /packages/subscriptions/sync`, which a PEER may send) checks the catalog against the key and the last `seq`, fetches every archive the channel holds by digest, installs the set as ONE install through the distro's door (`installPackages`), source ref `subscription:<id>`, and uninstalls what the channel dropped; `GET /packages/subscriptions` is the fleet's view (applied release, `diverged` items). WHOSE IT IS (stadeum plans/software.md §5, item 15): the `PUT`'s actor (`resolveActor`; an `actor` in the body is 400) is recorded as the subscription's `actor`, and every sync installs as that person's own install would (`deps.install(…, { door: "distro", actor })`): they own each workflow a release adds, so the package's schedules run as them (`runsAs`, src/workspace.ts), a workflow already here keeps its owner (an admin's choice survives a release), and the gate reads what their runs will (`deps.secret(name, actor)`: theirs, then the deployment's, then env). A `git+` branch of theirs is read with their OWN value of the secret that serves its host alone (`deps.gitSecret` names it, `deps.own` reads the actor-secret store; never the deployment's value of that name), and a private one they have no token for fails `package_repo_denied: … — this subscription is <actor>'s, and is read with their own <NAME> alone …`, saying what to do. A later `PUT` by another person hands it over (the next read and what later releases add are theirs; the workflows here move only when an admin gives them an owner). One nobody made (the key with no actor, a boot or distro subscription) has no `actor`: it reads the deployment's value as before, and what it installs has no owner, so its schedules launch nothing until an admin gives one. A publisher pings every peer on file after a publish or a channel move. A subscription may follow a git BRANCH instead (plans/followed-repos.md §1, work item 1): `{ ref }`, a `git+<repo>[@<branch>][#<folder>]` ref, read with the token for its host (the `GET` shows the secret that serves it as `tokenSecret`, none when no secret does; a catalog's shows `token: boolean`; a `tokenSecret` in the `PUT` is refused, `TOKEN_SECRET_GONE`). `subscriptionProblem` refuses both shapes at once, a ref `parseGitRef` refuses, and a full commit sha; a TAG is only known after a fetch, so the first sync refuses it (`resolvePackage(…, { branch: true })` resolves the remote's branch alone) and installs nothing. `syncGit` reads the ref as serve mode's `fetchRef` does, `known` the commit and digest applied (an unmoved branch reads nothing out of git): the same digest is `current` (the new commit recorded, nothing installed: a commit outside the package's folder), any other is ONE install through the distro's door with ref `subscription:<id>` and the commit (`deps.install`'s refs carry it; install.ts records a caller's `commit` on each version's `upstream`) — an older commit too, so a branch moved back is a rollback — then what it installed under another name goes (`dropOthers`, shared with the catalog path). State: `applied` is `{ ref, commit, digest, at, packages }`, no `seq`; a failure keeps what is installed, as `error`. A changed `ref` (or `key`) starts the state over at `set`. Read at the `PUT`, at boot, every `STRUT_DISTRO_POLL_MINUTES` (`syncAll()`), and on `POST /packages/subscriptions/:id/sync` (full scope; the outcome with `from`/`to` commits) — never on the publisher's ping, which calls `syncAll({ git: false })`: no publisher pings a branch, and a host that moves it in its own window (Stadeum: `STRUT_DISTRO_POLL_MINUTES=0`, a nightly sync by id) must not be moved by a peer. THE SECRETS GATE (plans/followed-repos.md §2, work item 2): every sync, of either kind, checks each package of its set against `requires.secrets` before it installs (`gate`), reading the deployment's secrets as an install's `missing` does (`deps.secret`, the secrets capability, which falls back to strut's environment; never the subscription's own store; an empty value is none, `hasValue`, since compose hands strut an unset setting as `""`) — for a person's subscription, as a run of theirs reads them. A package that lacks one WAITS: nothing of it goes in (no step, workflow, app or Concept page), one this subscription installed earlier goes out through the distro's door (`dropOthers`, edits kept by the uninstall rule), the state says `waiting: { secrets }`, and the outcome's status is `waiting`. In a `pk:` channel the gate is per package, the set walked requirements first: a package that requires a waiting package of the set waits too, and the rest of the channel goes in (status `waiting`, with `result`). The catalog's sealed `requires` is what a `pk:` release is gated on, so a waiting archive is never fetched; a package required from outside the channel, resolved from its source hint at install, is not gated. `applied.packages` is what went in, not what waits, and the early return (`current`, or `waiting` again) needs both the digest unmoved and `applied.packages` equal to what may go in now (`sameAs`), so a secret set or removed since the last sync installs or takes out the package with no new release. A take-out that fails is a warning, as a channel's drop is, and is not retried until the release moves. A person's install (`POST /packages/install`) is not gated: its `missing` reports. ONE PACKAGE, ONE SUBSCRIPTION (stadeum plans/software.md §5 item 5): the gate also leaves out a package another subscription here holds — its `source.ref` is `subscription:<x>`, `x` a subscription on file or a part of one (`holders`); the fold is read only when another exists — and says so as `held: [{ package, by: "subscription:<x>" }]` on the state and the outcome, status `held` (after `waiting`, before `applied`): nothing of it is installed or removed by this one, and the next sync after that one lets go (it is deleted, or its release drops the package) takes it. One nobody follows — a person's install, the boot list, a subscription since deleted — a subscription takes, as before: the distro's door stamps its versions with the subscription's source even at the same digest (install.ts), so it reads as the subscription's from that sync on. BUNDLES (stadeum plans/software.md §3.3, §5 item 5): a `git+` subscription whose branch holds a bundle (format.ts) follows each ref it lists as a PART — a subscription in all but its record: id `<id>/<repo name>-<8 hex of refSource>` (`partIdOf`: the same at any branch, and a `/` no top-level id has), the bundle's `actor`, its own state file, installs recorded as `subscription:<part id>`. `syncGit`, reading a bundle, hands it to `syncBundle`: what the subscription installed under its own id (a branch that held a package before) and every part the release no longer lists go through the distro's door (`dropOthers` with the listed part ids, forks kept — a part stopped as `DELETE …?uninstall=1` stops a subscription; its state file goes), the state is written with `applied.bundle: { package, version, refs }` (`packages: []`: nothing of the bundle is installed; `at` moves only with its digest), then each listed part is synced by `syncGit` in the bundle's order, inside the bundle's one-at-a-time slot, whether or not the bundle moved, and only then is the bundle's `checkedAt` written (a page that waits for it to move waits for every part): so a part moves when its own branch does, gated on its own secrets, with its own error, and one that waits or fails holds back no other. A part whose branch holds a bundle fails, `package_is_bundle: … a bundle lists packages, not bundles`. A branch that held a bundle and now holds a package drops every part (`dropOthers` with none listed). The outcome carries `parts` (each part's `SyncOutcome`), the union of their `waiting` and `held`, `from`/`to` the bundle's commits, and status the most pressing of the bundle's own (`applied` when its digest moved) and its parts' (`error`, `waiting`, `held`, `applied`, `current`); `error` is only the bundle's own read. `GET` lists top-level subscriptions only: a bundle's `parts` are each a `SubscriptionInfo` as a subscription to that ref alone reports, and the bundle's `packages`, `waiting` and `held` are its parts' together, so a page shows the bundle and its parts knowing nothing of what it holds. `delete` waits for a sync under way, then stops the parts with it: with `uninstall`, every package whose source is `subscription:<id>` or `subscription:<id>/…` goes (forks kept); without, they stay, the distro's, followed by nothing, and a later subscription takes them (the same id gets the same part ids back).
