# The graph layer: Neo4j and LadybugDB

The graph engines behind one set of seams, the writers and the reader, embeddings and search, the graph workspace, and the `graph/*` and `memory/*` steps.

This file is the reference for one area of strut; [AGENTS.md](../AGENTS.md) is the
index. A change in this area updates this file, not AGENTS.md.

## Stack

| Concern | Choice |
| --- | --- |
| Embedded graph | `@ladybugdb/core` (LadybugDB, the Kuzu fork), an **optionalDependency** with a native addon: for the `memory/*` lib steps (`<dataDir>/memory/graph.lbug`, or `STRUT_MEMORY_DB`), workspace custom steps that keep a local graph, and the Ladybug graph backend (plans/ladybug-backend.md, BUILT 2026-10-14: the graph layer strut owns — the workspace store, runs and jobs, claims, Concepts — on one file under `dataDir`, `STRUT_WORKSPACE_BACKEND=ladybug`, the desktop package's default — `src/graph/ladybug/`, wired by `src/graph/wiring.ts`; an existing filesystem workspace is imported into the file at that boot, `src/graph/fs-import.ts`). `memory/_db.ts` and `graph/ladybug/db.ts` `await import()` it on first use (the graph handle falls back to the platform package, so an install with scripts blocked still loads); registry build never loads it, and without it a memory step fails with an install hint. In the darwin desktop package (addon + bundled OpenSSL + the `vector` and `fts` extensions in `native/`, plans §2.3) only built-in `build/` steps reach it: a workspace custom step outside the bundle resolves `strut`/`vein` through strut-resolve-hook.ts and nothing else |

## Files

What each file and folder in this area is, in the order of the tree.

### `src/graph-writes.ts`

GRAPH WRITES, HEARD (plans/live-feeds.md §2, §3): `bindGraph` — the runner's per-run view of `services.graph`, its `nodes` / `edges` writers wrapped (a Proxy per mutating call: write, writeMany, update, softDelete, deleteNode; edges write, writeMany, update, delete, move) so each write is noted when it returns; a step calling `graph/*` steps through `ctx.registry` passes the same ctx and is heard too. `graphReporter` gathers a run's writes, types what it can (the run's own writes, then `reader.getNode`, ≤ 50 a send), drops strut's own types (`isQuietType`: `Strut*`, Claim / Check / Evidence, Thing, Schema), and sends a second after the last write (≤ 5 s after the first, and at the run's end): `job.update { kind: "graph", id: <runId>, state: "written", detail: { writes, types, refs } }` to the run's job — cumulative, so the outbox's coalescing loses nothing; Hive re-reads a canvas card's trees on it — and every write to the deployment's `GraphChangeFeed` (`services.graphChanges`, 5 000 writes), which `graph/changes` and `GET /graph/changes` read (ids, types, time). A proposal's apply is heard the same way (`id: proposal:<id>`). The view also wraps the ontology's writers (`schemaSource`'s writes, the resolver's `createEdgeSchema` — what `createNodeSchema` and a `create-triplet` that adds an edge rule go through), noted as a `Schema` change, quiet to the job and the feed; and when the bag has a `history` (src/history.ts) a send that held a write the history RECORDS (`historyRecords`: a Concept, a `PARENT_OF` edge, a `Schema` change, a Claim or Check or their edges — a write whose type the send could not learn counts) tells it "run R flushed" (or "proposal P") and who, before strut's own types are dropped; a send of instances alone tells it nothing and takes the view off its waiting list (`skipped`), since a snapshot reads every Concept. A view's first write puts it on the history's waiting list (read-your-writes). Not heard: raw Cypher, another process's writes

### `src/steps/lib/memory/`

memory/remember, recall, get, ontology, forget, merge, export, import, lexicon, attributes: an agent's long-term memory on embedded LadybugDB (_db.ts: lazy handle, schema, migrations, `memoryWrite`; _ontology.ts: the Ontology rows — entity types + predicates, aliases, cardinality one/many, unknown terms kept `proposed` — and `vocabulary()`, the one place steps read behaviour from, cached per database until a write to the Ontology commits: a type's `parent` (single, child wins), `naming`, `role: user` (singleton matching, the default speaker, refused by forget/merge), `role: dictation` (the type dictation makes a new word as: memory/lexicon's `lingo_type`), a predicate's `role: alias` (its fact text names the subject) and `role: mishearing` (heard_as: how dictation mishears the subject, the wrong text in `Fact.value` and the written form it stands for in `Fact.form`, NULL for the name — never an alias, so nothing resolves, recalls by name or pairs on it); _ontology-seed.ts: the seeded terms, add-only plus a NULL-only backfill; _lang-en.ts: language data, `STRUT_MEMORY_LANG`). No step names a type or predicate: memory-ontology.test.ts fails on one in a string literal. Graphiti-style Episode → Entity ← Fact with world time (valid/invalid, NULL unless the words gave one) and record time (created/expired): a fact is superseded, never overwritten, and one whose end has passed is stored past (a current fact that began before the one held is history); an episode has a `speaker` (default the user, NULL when the user has no entity yet; first person means the speaker); remember, merge and forget are one transaction each on a write connection of their own (`memoryWrite`); forget is a soft delete with a reason; merge leaves the duplicate as an ALIAS_OF. lexicon is dictation's vocabulary in one read (Peel's): each live entity's cased written forms (its name and its name facts' values), its mishearings, `dictation_off` (attributes.dictation, written by attributes, which sets or clears entity attribute keys) and ranking inputs, plus the mishearings forgotten with reason `undone` so they are not learned again. export / import (_snapshot.ts) move the whole graph between struts: export, in the writes' queue (`memoryExclusive`), CHECKPOINTs and writes one .tar.gz (manifest.json + EXPORT DATABASE's Parquet) to `<memory folder>/snapshots/`, kept until the next export; import loads one into an EMPTY graph only (no Entity, Fact or Episode rows), and a failure part-way leaves it empty. Owner-only folder

### `src/steps/lib/graph/`

graph/* knowledge-graph steps over src/graph (the strut-native twins of the mcp lab's jarvis/* steps — same names, inputs, outputs, except graph-search: its hits also carry a code node's `file`, `start`, `end` (0-based lines, as stakgraph stores them), and it takes `exclude` (path parts or file-name globs to leave out) — plus nine strut-only ones: changes, the graph writes made through strut after a cursor (`ctx.services.graphChanges`, src/graph-writes.ts — ids, types, time; `types`, `since`, `wait`; plans/live-feeds.md §3); query, ONE read-only Cypher query as a workflow step (`readQuery`, src/graph/query.ts — the chat's `graph_query`; rows keyed by column, strings whole, `maxRows` ≤ 1000 with `truncated`, a write or a failed query FAILS the step; never served to an app page, which reads by type with `find`; the `builder` seed grants it, since with no raw read the job wrote custom steps that opened the graph themselves); delete-edge removes one edge (by `edge_ref_id`, or source + type + target, the locator edit-edge takes), delete-node soft-deletes a node of ANY type in the namespace with its edges (the node writer's `deleteNode`; `softDelete` keeps its strut-domain guard) — the two writes hive's `graphEdgeDelete` / `graphNodeDelete` proposals needed (plans/proposals.md §6b), create-schema registers/extends a node type, edit-edge patches an edge's properties, move-node re-homes a node (the one edge that places it — any type, either direction — is muted and written again to the new place, one transaction, cycles refused; graph reads skip muted edges, as jarvis's do), walk gathers context for a goal hop by hop with a decision model (jev via experimental_evaluate, or a wrapped LLM) judging relevance/next/enough — plans/graph-walk.md — find, the nodes of ONE type whose properties match (`src/graph/find.ts`: `where` field → value or `gt`/`gte`/`lt`/`lte`/`in`/`contains`, `orderBy`, `limit` ≤ 500 + a `cursor`, `count`; fields are the type's schema attributes, `ref_id`, `created_at` (`date_added_to_graph` accepted as its old name), so nothing the caller writes reaches the statement; one dialect-helper statement on both engines; no provenance — a list is not what the caller named; plans/apps.md §4.3) — and two strut-only INPUTS on graph-get: node_type + name, an exact lookup by key for types keyed by name, never a search; and `children: <EDGE_TYPE>`, which adds the nodes it points to along that edge as { ref_id, node_type, name, description } sorted by name — a node and its table of contents in one call; and `required: true`, for a workflow that cannot go on without the node: every failure the step returns as a string for a model — not found, an unknown type, a malformed lookup — is thrown instead); _shared.ts's `graphCtx` takes `ctx.services.graph` — the backend the server wired, a Neo4j or the desktop's Ladybug file — and only without one opens a Neo4j from env; graph-steps.test.ts is a live end-to-end test

### `src/graph/`

the graph layer on TWO engines behind one set of seams (plans/ladybug-backend.md §4): Neo4j over bolt, jarvis-compatible and no jarvis in the loop (plans/jarvis-graph-compat.md), and a LadybugDB file (`ladybug/`) holding only what strut owns. Opt-in via openGraphBackend

### `src/graph/engine.ts`

the seams: `GraphEngine` (kind, namespace, query, tx, the nine `Dialect` helpers — node / isType / typeOf / edgeType / live / edgeLive / int / lower / project, no tenth) + `NodeEngine` / `EdgeEngine` / `SchemaSource` (+ `ClosedRegistry`, a source that is code), the statements the writers and the resolver cannot write neutrally — and the batch reads a reconcile over hundreds of nodes needs (`NodeEngine.readByKeys`, `EdgeEngine.liveEdgesOfMany`), one statement where a loop of `refByKey` / `readRaw` / `liveEdgesOf` was one transaction per node. Pure code above the seams is shared; a `GraphBackend` IS a `GraphEngine`

### `src/graph/neo4j-engine.ts`

the Neo4j implementation: today's Cypher moved behind the seams as it was (the UNWIND-MERGE template, the IS_ALIAS rewrite, shortestPath, the `:Schema` meta-graph reads and writes); wraps Integers from the schema, so `int()` lives nowhere else. `asEngine(bolt)` for a bare Bolt

### `src/graph/ladybug/`

the LadybugDB engine (plans/ladybug-backend.md, ruling 6 as amended 2026-10-28: a DYNAMIC ontology, plans/memory-in-workspace-graph.md PR A): ontology.ts — the ontology IN the file, as on Neo4j: a type is a `Schema` row of the `Node` table (`node_type: 'Schema'`, its fields columns, its key spec the row's `key_spec`, its declared attributes one JSON column `attributes`), its parent and every allowed `S -[E]-> T` an edge of the ontology's own rel table `SCHEMA_EDGE` between two Schema rows — a parent link marked `is_parent` (read only by the ancestor walk), a rule unmarked with `edge_type` E (read only by the edge-rule lookups), apart from the data's rel tables so a read of an edge type never meets the ontology; `*` the wildcard; a declared attribute adds its column (`ALTER TABLE Node ADD`, one name one column type everywhere — a clash is refused), a new edge type its rel table, both in the caller's transaction; `LadybugCatalog` caches the file's columns and rel tables per handle (dropped on every schema write; a write that names one it lacks reads it again on its own transaction); `seedOntology` seeds registry.ts at open, once per seed version (stamped `ladybug_ontology_seed:<hash>` in `Migration`): planned whole before any DDL (a seed type a runtime type got to first — a clashing column, a name or alias — is skipped and warned, never a failed open), seed types set back to the seed's keys (runtime attributes kept), edge rules add-only. A Schema row is no node: `getNode`, neighbors, counts, `softDelete` and the edge writers' ref_id lookups leave the ontology out. registry.ts — the SEED in code: the nineteen types a new file holds (the ten Strut types the store and projector need, Claim / Check / Evidence, Concept — with exactly the attributes strut reads and writes, no Thing vestiges, no per-stem vectors), the twenty-two edge types (the Concept tree as `PARENT_OF`, parent → child, as jarvis keeps it and every reader walks it; `CHILD_OF` too; `DERIVED_FROM`, what a work product was made from), Concept's `unique_source_id` (a seeded page's stamp), `nodeColumns()` (the columns a new file is made with: generic, Schema fields, one per seed attribute; the module refuses to load on a type conflict), `ontologySeed()` (Thing, then the seed types as flat Schema maps, the edges, the stamp); db.ts — the handle: one Database per absolute path on globalThis, owner-only folder, the addon or its platform package (CI's --ignore-scripts), `vector` + `fts` REQUIRED to open (`STRUT_LADYBUG_EXTENSION_DIR`, else the pinned copies: extensions.ts — sha256 per platform for the installed core, Ladybug's own builds taken from its extension-repo image at a digest and held on a stakwork/strut release, downloaded and verified into the model cache through src/audio/download.ts; no pin for the core or platform → `INSTALL`, with a warning), the DDL (one `Node` table, `ALTER ADD` per column so a new seed attribute lands on restart; one rel table per edge; `Migration`), two indexes, the ontology seed, a write queue whose `withWrite` refuses every statement after a failure (the engine rolls back and the next would auto-commit), `readOnly()` = a connection of its own whose every statement runs in `BEGIN TRANSACTION READ ONLY` (NOT a second read-only `Database`: one reserves `MAX_DB_SIZE` of address space per open — 1 TB; at the addon's default 8 TB a process fits eight to ten, and `close()` never returns it), rows made plain (INT64 → number, a struct's nulls and `_label`/`_id` dropped); engine.ts — the dialect (`(n:Node {node_type: 'T'})`, `deleted_at IS NULL`, `label(r)`, CAST), nodes (pre-read `(node_type, key)` → CREATE the misses in one UNWIND, SET the hits; soft delete = `deleted_at` then the edges in three statements), edges (MERGE on `edge_key` — the rows of one shape in one UNWIND, a repeat in the batch or a lone row one at a time — typed columns only — an unknown edge property is an error, no alias rewrite, no flags, `SHORTEST` for the cycle check; an edge type needs its rel table), and the schema source = `LadybugSchemas` over ontology.ts (`holdsStrutTypes`: the resolver reads Strut types from the rows, not strut-schemas.ts; no jarvis allowlist); reader.ts — `LadybugReader`, the read surface over the one table: lookups, `namesLike`, neighbors and counts (two directed statements, `importance` order in TS), schemas from the Schema rows (the root Thing left out), columns from the catalog, and `search` = `QUERY_FTS_INDEX` (all words required, any-word fallback, no fuzzy) + `QUERY_VECTOR_INDEX` (`1 - distance`), both filtered after their top-k so every filter over-fetches both halves, into the shared fusion. One namespace; a domain is the types whose Schema names it; hidden = `deleted_at`, no per-field vectors; Schema rows are never hits. No migrations, no pass

### `src/graph/strut-schemas.ts`

the 14 Strut node types (StrutApp + StrutAppVersion, plans/apps.md §1.3; StrutJob: exact_key on the job id, indexed title + summary, plans/job-index.md §6; StrutArtifact the newest: one per (job, artifact id), exact_key, the fold's newest version, `HAS_ARTIFACT` from its job and `DELIVERED` from each run whose output declared it; StrutProposal the newest: one per proposal, exact_key, a projection of its record — `IN_RUN` the run that made it, `ACCESSED` each node its apply wrote, `proposal_status` never `status`, plans/proposals.md §2) + 26-row edge registry (label registry in plans/generic-storage.md; `IN_CHAT` from a builder chat's `StrutTurn` and from an assistant conversation's `StrutAgentSession`, one `StrutChat` type for both, its `kind` saying which); author-time checks. The flag never reaches the Schema node

### `src/graph/schema-seed.ts`

idempotent domain registration through `SchemaSource`: Thing root, Schema nodes, CHILD_OF, the migration stamp; the constraints and vector/fulltext indexes are Neo4j DDL (`engine.bolt`). On a graph with no jarvis `About` node it also creates `strut_search_text_index`, the one keyword index the reader uses there, and `createNodeSchema` then makes no per-domain fulltext index. Also the seed types (seed-types.ts), each created through `createNodeSchema` only when no Schema has its name, and each of their edge rules only where the graph does not already allow that edge — so a graph jarvis seeded keeps its own rows and gets none of ours. Returns `mode: "file"` at once on a store that seeds its own Strut types (Ladybug)

### `src/graph/seed-types.ts`

the types BOTH engines seed beside the Strut ones (plans/ontology.md): Claim, Check, Evidence (the claim layer) and Concept, under jarvis's names and key specs with the attributes strut writes and reads, their 16 edge rules, and their Neo4j domains (Epistemic, General). Ladybug's registry.ts seeds them at open, schema-seed.ts on Neo4j; every other type is created at runtime

### `src/graph/node-writer.ts`

§6 validation gate + node_key composition (jarvis's sanitizer, verbatim; hex tokens for an `exact_key` type — `keyToken`) + Data_Bank + the create/upsert/restore/update semantics; issues no Cypher — `NodeEngine` does (`neo4j-engine.ts`, `ladybug/engine.ts`); softDelete (Domain_strut only) + retirePlannedEvidence. A write may ask for `embed: "later"`: its text is written, its vectors cleared and handed to the backend's background embedder (`NodeWriterOptions.later` — Neo4j's pass `soon`, a Ladybug file's backfill, both in a worker thread), for a caller writing hundreds of nodes at once (MiniLM is ~9 ms a text on a laptop's CPU, inline on the main thread); with no background embedder, or on a caller's transaction, it embeds inline

### `src/graph/edge-writer.ts`

the edge rules (closed Strut registry for Strut sources, the resolver's edge schemas for the rest — jarvis's edge allowlist only on a graph jarvis shares, one holding jarvis's `About` node; elsewhere every edge needs a rule, plans/ontology.md ruling 1), stamps, update() = jarvis PATCH /v2/edges/:ref_id (stamps protected), move() with its cycle check; issues no Cypher — `EdgeEngine` does (on Neo4j: MERGE by edge_key with the IS_ALIAS rewrite, ON CREATE only, a legacy muted edge made live)

### `src/graph/schema-crud.ts`

createNodeSchema(): register a non-Strut node type like jarvis POST /v2/schema (parent, attribute grammar, node_key, CHILD_OF, constraint) or add-only extend an existing one, on both engines (on Ladybug a new attribute is a new column); on Ladybug a name or `aliases` entry that is already another type's name or alias is refused, and a `managed_by` type only takes its owner (plans/memory-in-workspace-graph.md decision 9; `SchemaSource.typesNamed`, Ladybug's — Neo4j keeps jarvis's rules)

### `src/graph/exact-key-migration.ts`

one-shot boot re-key of existing StrutWorkflow/-Version/StrutStep/-Version nodes from the sanitized name to the exact (hex) key — ledger-stamped, idempotent, every namespace, soft-deleted nodes included; ref_ids, edges and the Schema nodes untouched

### `src/graph/embeddings.ts`

local all-MiniLM-L6-v2 via transformers.js, tokenized like sentence-transformers (256 incl. specials), 2 intra-op threads; + the EMBEDDING PASS (plans/semantic-search.md §1): a timer in the serving process that keeps `Data_Bank` + `text_embeddings` + the domain label current on EVERY node of a Schema-marked type, whoever wrote it (stakgraph's ingest, jarvis, an import) — stale = the stored text ≠ the writer's composition from the Schema's `index` fields, or no vector — strips the no-embed types (`embed: false`: `Turn` via its Schema, `StrutToolCall` / `StrutTurn` in code), pages by `node_key` (an index seek per page, never a scan), works 15 s a minute (the budget checked between batches of 100 rows), sweeps hourly (code types first), embeds NEWCOMERS by `date_added_to_graph` between sweeps (marked labels only, a `>=` cursor: stakgraph stamps a whole ingest batch alike). Its inference runs in a WORKER THREAD (`WorkerEmbedder`, over `ModelWorker` — src/model-worker.ts): onnxruntime-node's `run()` is synchronous, and on the serving process's main thread every forward pass stalled every request (swarm38, 2026-10-11: mcp's `/lab/health` 0.34 s → 1.74 s during a tick); the writer and search keep the in-process model. `GET /graph/embeddings` is its status; `STRUT_GRAPH_EMBEDDINGS=off` turns it off with the embedder. `soon(refs)`: the nodes a writer left without a vector (`embed: "later"`) are embedded in the next tick, ahead of the sweep and the newcomers (an updated node's stamp is old, so it is no newcomer)

### `src/graph/search.ts`

the read surface — `GraphReader` the INTERFACE every consumer reads through (`backend.reader`), `Neo4jReader` jarvis's read paths over bolt, the ranking shared with `ladybug/reader.ts`: hybrid search (RRF + title boost + usage tiebreak; a question of 4+ words fuses the keyword half at half weight, quoted spans and words the analyzer would split are phrases — `fusionWeights`, `queryParts`), get/neighbors/counts, ontology, namespaces. Routing (`routeIndexes`): the keyword half of a graph strut alone holds (no jarvis `About` node) reads ONE fulltext index over every node's composed search text (`strut_search_text_index` on `Data_Bank`, created by schema-seed.ts), its `type` and `domains` a WHERE after the index with the same over-fetch as vectors — so a runtime type is keyword-searchable on its declared `index` fields whichever type came first in its domain, as on a Ladybug file (plans/ontology.md item 4); a graph jarvis shares keeps jarvis's per-domain attribute indexes, which also cover fields outside a type's own `index` (a Function's `body`). A typed search reads the requested types' DOMAIN vector (and, on a jarvis graph, fulltext) indexes with an over-fetch (`overfetch`: k from cap×10 by ×4 to 2,000 — the database cannot filter a vector query, so `type` is a WHERE after the nearest-k cut), an untyped one the global `text_embeddings_vector_index`. `exclude` leaves results out by their `file` (`excludeRegex`: a path part matches whole `/` segments, a pattern with `*` or `?` the file name, case-insensitive; a node with no `file` stays) — one `=~` in the same WHERE, so a search with it over-fetches both halves, the keyword one's `limit` like a vector `k`. `linked` keeps results with a live edge of a type to a live node of a type (`parseLinks` → `linkedClause`: `EDGE>Type` leaves the result, `EDGE<Type` arrives at it, any one passes, the type resolved like `type`'s) — one `EXISTS` per entry in that WHERE, over-fetching the same way

### `src/graph/backend.ts`

openGraphBackend(cfg): `GraphConfig` is `Neo4jConfig | LadybugConfig` (`{ kind: "ladybug", path, namespace: "default" }`), overloaded per kind, cached per config. Neo4j: runs the migrations and the seeds on first open (strut bundles no jarvis library: plans/ontology.md), then STARTS the embedding pass (nothing waits on it; `close()` stops it). Ladybug: the handle's open IS the schema (DDL + the ontology seed) — no migrations, no pass; `reader` is the `LadybugReader` over its FTS + HNSW indexes, the writer embeds inline

### `src/graph/wiring.ts`

the default server's workspace from env: `workspaceBackendFromEnv` (`STRUT_WORKSPACE_BACKEND`: neo4j | ladybug | fs), `graphWorkspaceFromEnv` (Neo4j: NEO4J_*), `ladybugWorkspaceFromEnv` (the file at `STRUT_GRAPH_DB`, default `<dataDir>/graph/graph.lbug`, its own owner-only folder like memory's; then the fs import), `graphMaterializeDir` (`steps/_graph`)

### `src/graph/fs-import.ts`

the one-shot fs → graph import (plans/ladybug-backend.md §6 item 4, §7.1), a boot step: `FileWorkspaceStore.snapshot()` published through the GraphWorkspaceStore — every workflow version under its own label with description + provenance, then active / category / publisher / owner / cap / automations; every step version in label order, then the active one — and only once it all went through, the files moved to `<dataDir>/fs-workspace.imported-<ts>/` (the run store's `workflows/<name>/runs/` stay) and the `Migration` ledger stamped. ### `src/graph/query.ts`

The tool description and the prompt's "Graph backend" line say how nodes are laid out on each (`graphConventions`, ai/prompts.ts)
