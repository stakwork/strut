# The worker's language: Spanish first

> **Status (2026-11-18): BUILT.** A worker whose phone is in Spanish sees
> the Worker app in Spanish: its screens (strut/views' worker pieces), the
> form, the refusals, and what strut draws around it (sign in, the camera,
> the account widget, the Back bar). The admin's side stays English.

## What a worker sees, and whose words they are

| Layer | Where | Language |
| --- | --- | --- |
| The worker's screens | strut/views' `WorkerPage`, `WorkHome`, `WorkerTask`, `TaskPhotos`, `TaskForm`, `TaskReplyView` | The page's: `src/apps/views/src/lib/words.ts` |
| strut's UI around the frame | `SignInSheet`, `CameraSheet`, `AccountWidget`, `SoloApp`, AppHost's overlay | The page's: `web/src/words.ts` |
| A refusal | `TaskError`'s code and English sentence | The page says the code in Spanish; English keeps the server's sentence, which names the type |
| A form's problem | the kit's `answerOf` | `issue` (`required`, `number`, `integer`), said in the page's language |
| What a type says | its `title`, the task's `show`, the answer schema's titles and choices, a reply | The admin's, as written: never translated |

## How

- **The locale is already there.** MCP Apps' host context carries
  `locale`. strut's UI sends the link's `lang=`, else `navigator.language`
  (`pageLocale`), so Peel's web view of `?app=…&solo=1` sends the phone's.
  The kit reads it as `useLocale()`, and `<html lang>` follows it.
- **A screen's words are an object per language.** `{ en, es }`, English
  the type: `const es: WorkerWords`, and `{ en, es } satisfies
  Record<Lang, WorkerWords>`. A message missing from Spanish, or of another
  shape, fails tsc. A message is a string or a function. A function owns
  its word order and its plurals. English and Spanish have one and other
  alone, so `n === 1` is right for both. A language with more forms uses
  `Intl.PluralRules` in its own functions.
- **`Intl` does numbers and times.** `formats(locale)`: sats grouped as the
  region groups them (`1,234` in es-MX, `12.345` in es), `ago` and `until`
  through `Intl.RelativeTimeFormat` ("hace 5 min", "dentro de 3 h").
- **No library, no dependency, no change to the vendor layer.** The kit
  adds `LANGS`, `langOf`, `wordsFor`, `formats` (a fold) and `useLocale`,
  `useWords`, `useFormats` (hooks). An app the builder writes may use them
  too.
- **The server speaks codes.** Steps are MCP calls, which carry no
  language. A server that wrote Spanish would put words in two places, and
  the staff, the logs and the tests read its English. So the page maps a
  refusal's code to a sentence: the known codes have one in Spanish, and an
  unknown code falls back to the server's English.
- **A type's `title`.** Names are ASCII (`TYPE_NAME_RE`), so "Revisión de
  recibo" cannot be one. A type may carry a title, at most 80 characters,
  shown wherever the worker reads the type. It is set in strut/staff's
  editor or by `task/set-type`. With no title, the worker reads the name as
  before.
- **Spanish:** neutral Latin American, `tú`.
- **`lang=`** on a link overrides the phone. It is for an invite's link,
  screenshots and tests, and for a native host whose web view reports the
  wrong language.

## Not done

- **One server, workers in two languages, with different content.** A
  type's content is one language, the one the admin wrote it in. If two are
  ever needed, the content gets versions per language. Not before someone
  asks for it.
- **Peel's web view.** WKWebView may report `en-US` on a Spanish iPhone
  when the app bundle is not localized for Spanish. This is unverified.
  If it does, Peel adds `&lang=<Locale.preferredLanguages[0]>` where it
  builds the `?app=…&solo=1` link.
- **The admin's UI** (strut/staff, strut/earnings, strut's own screens)
  stays English.
